## 1. Goal

Let a signed-in user **capture** their groceries: create named grocery lists and add, view, edit, and remove the
items on them. This is the first real domain feature of Growcery. It adds basic CRUD exposed as REST endpoints.

### In scope
- CRUD for **grocery lists** owned by the current user.
- CRUD for **items** within a list.
- **Soft delete** for lists, with endpoints to view and restore deleted lists (D2).
- Per-user data isolation (a user can only see and change their own lists).
- EF Core entities, a migration, and integration tests.

### Out of scope (later specs)
- Sharing lists between users or households.
- Categories, aisles, prices, pantry/stock tracking, and recurring lists.
- Reordering items, bulk operations, and PATCH endpoints.
- Pagination, search, and filtering (lists are expected to be small for now).
- Permanently purging soft-deleted lists (a retention or cleanup job). Also soft delete for individual items.
- Optimistic concurrency / edit-conflict detection (D5).
- Any frontend, and any CORS configuration.

## 3. Domain model

### 3.1 `GroceryList` (`Models/GroceryList.cs`) ✅ implemented

| Property | Type | Rules |
|---|---|---|
| `Id` | `Guid` | PK, generated by the server |
| `OwnerId` | `string` | FK → `AspNetUsers.Id`, required, indexed, **never accepted from the client** |
| `Owner` | `ApplicationUser?` | Navigation |
| `Name` | `string` | Required, max 100. **Not unique.** A user can have two lists with the same name (D6) |
| `CreatedAt` | `DateTimeOffset` | Set on create |
| `UpdatedAt` | `DateTimeOffset` | Set on create and on every update, including item changes and restore |
| `DeletedAt` | `DateTimeOffset?` | `null` means active. Set on soft delete, cleared on restore (D2). Indexed |
| `Items` | `List<GroceryListItem>` | Navigation. Items are **kept** when the list is soft-deleted. The DB cascade only applies if a list row is ever physically removed |

### 3.2 `GroceryListItem` (`Models/GroceryListItem.cs`) ✅ implemented

| Property | Type | Rules |
|---|---|---|
| `Id` | `Guid` | PK, generated by the server |
| `GroceryListId` | `Guid` | FK → `GroceryList.Id`, required. Covered by the unique index below |
| `GroceryList` | `GroceryList?` | Navigation |
| `Name` | `string` | Required, max 100 (e.g. "Milk"). Unique per list (D1) |
| `NormalizedName` | `string` | Server-set to `Name.Trim().ToUpperInvariant()`, max 100. **Never exposed in responses.** Internal whitespace is **not** collapsed, so "Oat  milk" and "Oat milk" are different names |
| `Quantity` | `decimal?` | Optional. When set, must be > 0 with **at most 2 decimal places** (B2). `numeric(10,2)` |
| `Unit` | `string?` | Optional, max 20 chars (e.g. "kg", "L", "pack") |
| `Notes` | `string?` | Optional, max 500 chars |
| `IsPurchased` | `bool` | Defaults to `false` |
| `CreatedAt` | `DateTimeOffset` | Set on create |
| `UpdatedAt` | `DateTimeOffset` | Set on create and on every update |

### 3.3 `ApplicationDbContext` ✅ implemented
- `DbSet<GroceryList> GroceryLists` and `DbSet<GroceryListItem> GroceryListItems`.
- `OnModelCreating` calls `base.OnModelCreating(builder)` first (Identity needs it). It then configures:
  - max lengths and decimal precision
  - indexes on `OwnerId` and `DeletedAt`
  - a **unique index on `(GroceryListId, NormalizedName)`** (D1)
  - cascade delete from user to lists and from list to items
- **Global query filters** (D2):
  - `GroceryList`: `DeletedAt == null`.
  - `GroceryListItem`: `GroceryList.DeletedAt == null`. This matches the list filter so items of a deleted list can't
    be read directly, and it removes EF Core's warning about a filter on the required end of a relationship.
  - Only the "deleted lists" and "restore" endpoints use `IgnoreQueryFilters()`, and they still filter by `OwnerId`.

### 3.4 Timestamps (B3)
- PostgreSQL `timestamptz` stores **microseconds**, but .NET `DateTimeOffset` has 100 ns ticks. If full-precision
  values are saved, the POST response and a later GET return different timestamps.
- Add one helper, `Data/Timestamps.cs` → `public static DateTimeOffset UtcNow()`. It returns `DateTimeOffset.UtcNow`
  truncated to whole microseconds (`now.AddTicks(-(now.Ticks % 10))`).
- **Every** `CreatedAt`, `UpdatedAt` and `DeletedAt` assignment uses it. Don't call `DateTimeOffset.UtcNow` directly
  in controllers.
- Offset is always `+00:00` (Npgsql rejects non-zero offsets for `timestamptz`).

## 4. API contract

All endpoints:
- Require authentication (`[Authorize]` on the controller).
- Consume and produce `application/json`. Put `[Consumes("application/json")]` and `[Produces("application/json")]`
  on each controller. A body with any other content type gets `415` (see §6 for why this matters).
- Scope every query to the current user: `OwnerId == _userManager.GetUserId(User)`.
- Return **`404 Not Found`** (not 403) when a list or item doesn't exist *or* belongs to another user, so the API
  doesn't reveal which IDs exist.
- Ignore any `id`, `ownerId`, `groceryListId`, `createdAt`, `updatedAt` or `deletedAt` sent in a request body. The
  request models don't have these properties, so they're dropped during model binding.
- Every action declares its responses with `[ProducesResponseType]`: the success type, plus `ProblemDetails` or
  `ValidationProblemDetails` for each error code in the tables below. Swagger then documents them.
- **Concurrency: last write wins** (D5). There is no version or ETag check. Two simultaneous PUTs both succeed, and the
  later one overwrites the earlier.

### 4.1 Error format (D4)

Every non-2xx response is RFC 9457 **ProblemDetails** (`application/problem+json`):

| Status | When | How to produce it |
|---|---|---|
| `400` | Validation failure | Automatic `ValidationProblemDetails` from `[ApiController]` (per-field `errors`) |
| `401` | Not signed in | Cookie `OnRedirectToLogin` event writes ProblemDetails (§5) |
| `403` | Access denied (not expected to occur in this spec) | Cookie `OnRedirectToAccessDenied` event writes ProblemDetails (§5) |
| `404` | Missing, not owned, or soft-deleted | `return NotFound();`. `[ApiController]` turns it into ProblemDetails |
| `409` | Duplicate item name (D1) | `return Problem(statusCode: 409, title: "Duplicate item name", detail: "An item named '<trimmed name>' already exists in this list.");` |
| `415` | Body isn't JSON | Automatic from `[Consumes]` |
| `500` | Unhandled exception | Existing `UseExceptionHandler()` + `AddProblemDetails()`. Never expose exception details |

The existing account endpoints keep using `ErrorResponse`. Don't change them in this spec.

### 4.2 Lists — `GroceryListsController`, route `api/lists`

| Method | Route | Body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/api/lists` | — | `200` `GroceryListSummaryResponse[]` ordered by `UpdatedAt` desc, then `Id` | `401` |
| `GET` | `/api/lists/{id:guid}` | — | `200` `GroceryListResponse` (items ordered by `CreatedAt` asc, then `Id`) | `401`, `404` |
| `POST` | `/api/lists` | `CreateGroceryListRequest` | `201` `GroceryListResponse` + `Location` header (`CreatedAtAction`) | `400`, `401`, `415` |
| `PUT` | `/api/lists/{id:guid}` | `UpdateGroceryListRequest` | `200` `GroceryListResponse` | `400`, `401`, `404` (including a soft-deleted list), `415` |
| `DELETE` | `/api/lists/{id:guid}` | — | `204`. **Soft delete:** sets `DeletedAt` and keeps the list's items. `UpdatedAt` is unchanged | `401`, `404` (including a list that's already deleted) |
| `GET` | `/api/lists/deleted` | — | `200` `GroceryListSummaryResponse[]` of the caller's soft-deleted lists, ordered by `DeletedAt` desc, then `Id` | `401` |
| `POST` | `/api/lists/{id:guid}/restore` | — | `200` `GroceryListResponse`. Clears `DeletedAt` and sets `UpdatedAt` | `401`, `404` (not found, not owned, or not deleted) |

The `:guid` route constraint keeps `/api/lists/deleted` from matching `/api/lists/{id:guid}`.

### 4.3 Items — `GroceryListItemsController`, route `api/lists/{listId:guid}/items`

| Method | Route | Body | Success | Errors |
|---|---|---|---|---|
| `GET` | `/api/lists/{listId}/items` | — | `200` `GroceryListItemResponse[]` ordered by `CreatedAt` asc, then `Id` | `401`, `404` (list) |
| `GET` | `/api/lists/{listId}/items/{itemId:guid}` | — | `200` `GroceryListItemResponse` | `401`, `404` |
| `POST` | `/api/lists/{listId}/items` | `CreateGroceryListItemRequest` | `201` `GroceryListItemResponse` + `Location` header | `400`, `401`, `404` (list), `409` (duplicate name), `415` |
| `PUT` | `/api/lists/{listId}/items/{itemId:guid}` | `UpdateGroceryListItemRequest` | `200` `GroceryListItemResponse` | `400`, `401`, `404`, `409` (renamed to an existing name), `415` |
| `DELETE` | `/api/lists/{listId}/items/{itemId:guid}` | — | `204` | `401`, `404` |

- Any item write (create, update, delete) also sets the parent list's `UpdatedAt`, in the same `SaveChangesAsync`.
- **Duplicate names (D1):**
  - On `POST` and `PUT`, check whether any *other* item in the same list already has the same `NormalizedName`.
    If one does, return `409`.
  - A `PUT` that keeps an item's own name, or only changes its casing (e.g. "milk" → "Milk"), is **not** a conflict.
  - Also catch a `DbUpdateException` whose inner `PostgresException.SqlState` is `23505` (unique violation) and return
    the same `409`. This is the race path, and it's verified manually (D7).

### 4.4 Request models (`Models/GroceryListRequests.cs`)

Classes with DataAnnotations, following `AccountViewModels.cs`.

`[Range]` with `typeof(decimal)` **must** set both invariant-culture flags (B1). Without them, the limits `"0.01"` and
`"99999999.99"` are parsed with the server's culture. On a machine set to `en-ZA`, where the decimal separator is `,`,
that parsing fails and validation throws.

```csharp
public class CreateGroceryListRequest
{
    [Required, StringLength(100)]
    public string Name { get; set; } = string.Empty;
}

public class UpdateGroceryListRequest       // same shape as Create; PUT replaces the editable fields
{
    [Required, StringLength(100)]
    public string Name { get; set; } = string.Empty;
}

public class CreateGroceryListItemRequest
{
    [Required, StringLength(100)]
    public string Name { get; set; } = string.Empty;

    [Range(typeof(decimal), "0.01", "99999999.99",
        ParseLimitsInInvariantCulture = true, ConvertValueInInvariantCulture = true)]
    [MaxDecimalPlaces(2)]
    public decimal? Quantity { get; set; }

    [StringLength(20)]
    public string? Unit { get; set; }

    [StringLength(500)]
    public string? Notes { get; set; }
}

public class UpdateGroceryListItemRequest   // full replace of editable fields
{
    [Required, StringLength(100)]
    public string Name { get; set; } = string.Empty;

    [Range(typeof(decimal), "0.01", "99999999.99",
        ParseLimitsInInvariantCulture = true, ConvertValueInInvariantCulture = true)]
    [MaxDecimalPlaces(2)]
    public decimal? Quantity { get; set; }

    [StringLength(20)]
    public string? Unit { get; set; }

    [StringLength(500)]
    public string? Notes { get; set; }

    public bool IsPurchased { get; set; }
}
```

- **Whitespace-only names:** `[Required]` already rejects `null`, `""` and whitespace-only strings, because
  `AllowEmptyStrings` defaults to `false`. Don't add a manual check (B7).
- **Length limits apply to the raw input.** After validation, the controller trims `Name`, `Unit` and `Notes` before
  saving, and stores blank optional strings as `null`. The trimmed value is never longer than the raw one, so the DB
  limits still hold.
- **`MaxDecimalPlacesAttribute`** (`Models/MaxDecimalPlacesAttribute.cs`) is a small custom `ValidationAttribute`.
  A `null` value is valid. A `decimal` value is valid when `decimal.Round(value, places) == value`. Otherwise the
  error is "`{0}` must have at most N decimal places." It rejects `1.236` instead of letting PostgreSQL round it
  silently (B2).

## 5. Required change: API-friendly auth responses

By default, Identity's cookie handler **redirects** unauthenticated requests to `/Account/Login` with a `302`. An
API client should get a status code instead, with a ProblemDetails body (D4). In `Program.cs`, after
`AddIdentity(...)`, add:

```csharp
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Events.OnRedirectToLogin = context =>
        WriteProblemAsync(context.HttpContext, StatusCodes.Status401Unauthorized);
    options.Events.OnRedirectToAccessDenied = context =>
        WriteProblemAsync(context.HttpContext, StatusCodes.Status403Forbidden);

    static Task WriteProblemAsync(HttpContext httpContext, int statusCode)
    {
        httpContext.Response.StatusCode = statusCode;
        var problemDetailsService = httpContext.RequestServices.GetRequiredService<IProblemDetailsService>();
        return problemDetailsService.WriteAsync(new ProblemDetailsContext { HttpContext = httpContext }).AsTask();
    }
});
```

Check that the existing `AccountControllerLoginTests` still pass after this change. Their `401` comes from the
controller, not from the cookie handler, so it's unaffected.

## 6. Non-functional requirements

### 6.1 Security
- **CSRF.** The state-changing endpoints use cookie auth, so they rely on three layers:
  1. The Identity cookie is `HttpOnly` and `SameSite=Lax` (Identity defaults), so browsers don't send it on
     cross-site POST, PUT or DELETE requests.
  2. `[Consumes("application/json")]` rejects the form content types an HTML form can send cross-site
     (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`) with `415`.
  3. **No CORS policy is configured**, so browsers block cross-origin `fetch` with JSON bodies at preflight.

  Don't add a CORS policy in this spec. A future frontend spec must revisit CSRF (antiforgery tokens) if it enables
  CORS or cross-site hosting.
- **Transport.** In production the cookie must be `Secure`. The default `SecurePolicy = SameAsRequest` gives this as
  long as the app is served over HTTPS (`UseHttpsRedirection` and `UseHsts` are already configured outside
  Development).
- **Data isolation.** Every query filters by `OwnerId` (§4), and tests prove that another user gets `404` (§9).
- **No sensitive data in logs** (§6.2).

### 6.2 Logging
- Inject `ILogger<T>` into both controllers.
- Log each successful write (create, update, delete, restore) at `Information`, using structured properties:
  `UserId`, `GroceryListId` and `GroceryListItemId` where relevant. **Never log names, notes or other free text.**
- Log a `409` race-path mapping (§4.3) at `Warning`.
- Unhandled exceptions are already logged and turned into ProblemDetails by `UseExceptionHandler()`. Don't add
  try/catch blocks for logging.

### 6.3 Performance
- Build list summaries (`ItemCount`, `PurchasedCount`) with a projection query (`Select(... Items.Count(...))`), so
  it's a single SQL query. Don't load items and count them in memory, and avoid N+1 queries.
- Use `AsNoTracking()` for read-only queries.
- There's no pagination (D3). Revisit it if a user's lists or items grow into the hundreds.

## 7. Deployment and migrations

- **Development:** migrations apply automatically on startup (existing `Program.cs` behaviour).
- **Other environments:** startup does **not** migrate. Before deploying, apply the new migration with an idempotent
  script:
  ```
  dotnet ef migrations script --idempotent --output migrations.sql
  ```
  Then run `migrations.sql` against the target database. Review the script before the first production run.
- The migration only adds tables (it's additive), so it's safe to apply before the new code is deployed.
- **Rollback:** `dotnet ef migrations script AddGroceryLists InitialCreate` generates the down script, which drops
  both new tables and **destroys their data**. Only use it before any real data exists.

## 9. Test requirements

Add integration tests using `GrowceryWebApplicationFactory`, following `AccountControllerLoginTests.cs`:

- **Each test uses a unique username**, because the factory's InMemory database is shared across tests in a class.
- Authenticate through `AuthenticatedClientExtensions`, which uses the real `/api/account/register` endpoint. The
  default client keeps cookies, so later requests on the same client are authenticated.
- Check the status code **and** the body. For errors, also check `Content-Type: application/problem+json`.
- For `UpdatedAt` "advances" checks, compare `>`. The microsecond truncation (§3.4) makes a tie very unlikely, but
  don't rely on wall-clock sleeps.

Minimum cases:

**Auth and format**
- Unauthenticated `GET /api/lists` returns `401` (not `302`) with a ProblemDetails body.
- `POST /api/lists` with `Content-Type: application/x-www-form-urlencoded` returns `415`.

**Lists**
- `POST` with a valid name returns `201`, a `Location` header, and a body with the trimmed name.
- `POST` with an empty or whitespace name, or a name over 100 chars, returns `400` with `errors.Name`.
- `POST` with extra `id` or `ownerId` fields in the body ignores them: the list gets a server-generated ID and belongs
  to the caller.
- Two lists with the same name for the same user are both created (D6).
- `GET /api/lists` returns only the caller's lists, with correct `ItemCount` and `PurchasedCount`.
- `GET /api/lists/{id}` for another user's list returns `404`.
- `PUT` updates the name and advances `UpdatedAt`.
- `POST` then `GET` return identical `createdAt` and `updatedAt` values (B3).
- **Soft delete (D2):**
  - `DELETE` returns `204`. After that, `GET /api/lists/{id}` returns `404` and the list is missing from `GET /api/lists`.
  - `PUT` on a soft-deleted list returns `404`.
  - The list's item endpoints return `404` while it's deleted.
  - A second `DELETE` on the same list returns `404`.
  - `GET /api/lists/deleted` returns only the caller's deleted lists, with `DeletedAt` set.
  - `POST /api/lists/{id}/restore` returns `200` with `DeletedAt = null`, and the list's **items come back unchanged**.
  - Restoring an active list, or another user's deleted list, returns `404`.

**Items**
- `POST` an item to your own list returns `201`. `POST` to another user's list returns `404`.
- `Quantity` of `0` or less returns `400`. Leaving `Quantity` out (`null`) is allowed.
- `Quantity` of `1.25` is accepted, and `1.236` returns `400` (B2).
- **Culture (B1):** with `CultureInfo.CurrentCulture` and `CurrentUICulture` set to `en-ZA` for the test, `POST` with
  `quantity: 2.5` returns `201` and `quantity: 0` returns `400`. Restore the original culture in `finally`.
- `PUT` with `IsPurchased = true` persists and is shown in the list summary counts.
- `GET` or `PUT`/`DELETE` of an item using the wrong `listId` (a list the item doesn't belong to) returns `404`.
- `DELETE` returns `204` and updates the parent list's `UpdatedAt`.
- **Duplicates (D1):**
  - `POST` "Milk" and then " milk " to the same list returns `409` with ProblemDetails `title` "Duplicate item name".
  - The same name in a *different* list is allowed and returns `201`.
  - A duplicate returns `409` even when the existing item is purchased.
  - `PUT` that renames an item to another item's name returns `409`.
  - `PUT` that keeps the item's own name, or only changes its casing, returns `200`.
  - After an item is deleted, its name can be used again (`201`).

**Unit**
- `MaxDecimalPlacesAttribute`: `null` → valid, `1` → valid, `1.2` → valid, `1.25` → valid, `1.251` → invalid.

**Not automated (D7):** the unique-index race path. It's covered by the manual check in §8 step 7.

## 11. Open questions (to be decided with the user during planning — do not assume defaults)

Agents must not resolve these on their own. Ask the user, then move the answer to **Decisions** below.

_None. All open questions are resolved._

### Decisions

- **D1 — Item names are unique within a list** (decided 2026-09-28).
  - Names are compared **case-insensitively after trimming**, so "Milk", "milk" and " MILK " are the same item.
  - A duplicate on create, or a rename to a name that already exists, returns **`409 Conflict`** as ProblemDetails
    (D4), with `title` "Duplicate item name" and `detail` "An item named '<name>' already exists in this list."
  - A **purchased item still blocks** the name. The user un-ticks the existing item instead of adding it again.
  - The rule is enforced in two places: an app-level check, which is what gives the `409`, and a DB unique index on
    `(GroceryListId, NormalizedName)`, which stops races. EF InMemory doesn't enforce unique indexes, so the tests
    exercise the app-level check. See §3.2, §3.3, §4.3 and §9.
- **D2 — Lists are soft-deleted** (decided 2026-09-28).
  - `DELETE /api/lists/{id}` sets `DeletedAt` instead of removing the row. The list's items are kept.
  - The caller can view their deleted lists (`GET /api/lists/deleted`) and restore one
    (`POST /api/lists/{id}/restore`).
  - **Items are still hard-deleted** when removed individually. This keeps D1 simple: a deleted item's name is
    free to use again straight away.
  - Soft-deleted lists are **kept forever** for now. Purging is out of scope (§1).
  - Enforced with global query filters on `GroceryList` and `GroceryListItem` (§3.3). See §3.1, §4.2, §4.5 and §9.
  - Restoring a list that isn't deleted returns `404`, the same as a missing or unowned list.
- **D3 — No limits on lists or items** (decided 2026-09-28).
  - A user can have any number of lists, and a list can hold any number of items. Don't add count checks or quota errors.
  - The field-length limits in §3 and §4.4 still apply. Revisit this with pagination (out of scope, §1) if lists get large.
- **D4 — ProblemDetails for every error** (decided 2026-09-28).
  - Every non-2xx response from the new endpoints is `application/problem+json`, including `401`/`403` from the cookie
    handler (§4.1, §5).
  - `ErrorResponse` stays only for the existing account endpoints.
- **D5 — Last write wins** (decided 2026-09-28).
  - There are no concurrency tokens or ETags. Two simultaneous edits both succeed, and the later one overwrites the
    earlier.
  - This is acceptable while lists are single-user. Revisit it with list sharing (§1).
- **D6 — Duplicate list names are allowed** (decided 2026-09-28).
  - Lists are identified by ID only, and a user can have several lists with the same name (e.g. "Weekly shop").
- **D7 — The unique-index race path is verified manually** (decided 2026-09-28).
  - EF InMemory can't enforce unique indexes, so the `DbUpdateException` → `409` mapping has no automated test.
  - It's checked by hand against Postgres (§8 step 7) and tracked in the DoD. Add Testcontainers-based Postgres tests
    in a later spec if more DB-specific behaviour appears.
